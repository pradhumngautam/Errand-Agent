#### 1. What they're really testing

The task is a chat agent that books home services: plumbers, AC servicing, electricians. The chat is the easy part. What they're grading is whether the system stays correct when the AI model or the mock tools misbehave. The rubric comes down to these checks:

| Area | What must be true | Who enforces it |
|---|---|---|
| **Approval** | Nothing gets booked, cancelled or rescheduled unless the user approved the exact provider, slot and price. Any change to those cancels the approval. | App code, not the model |
| **Booking correctness** | No duplicate bookings, even with repeated "yes", retries or a restart. After a timeout, check the real status before doing anything. Never report success until it's verified. | Idempotency keys + saving state before acting |
| **Bounded execution** | Hard caps on model turns, tool calls and total time. Every way a run can end gives the user a clear message. | Code-level limits |
| **Prompt injection** | Provider reviews are treated as data. They can't change what the user asked for or who approved what. | Keeping untrusted text separate |
| **Memory** | Preferences persist across sessions. The user can view, correct and forget them. Explicit and inferred facts are kept apart. | Memory store with status/source fields |
| **Context budget** | 50+ stored memories and a long chat history, but a fixed token budget. Forgotten or unconfirmed inferred facts never reach the model. Log what was sent each turn. | Context builder + logged list of what was sent |
| **Proactive follow-up** | If a provider cancels, the agent notices without being asked, finds a replacement and gets fresh approval. | Background event handler |
| **Evals** | At least 20 scenarios run offline with a scripted model. They check outcomes and rules, not wording. The results table is generated by the test run. | pytest + rule checkers that read the traces |

**Design principle: the model suggests, the code decides.** The model understands the request, calls the read-only tools and writes the replies. It never calls `book`, `cancel` or `reschedule` directly.

#### 2. High-level flow

```
User msg ──► Intake (model pulls out the details as a partial update; a correction changes only one field)
               │  merged with explicit memory; ask only for what's missing
               ▼
          SEARCHING ── search_providers ──► code filters (budget, time window, area)
               │                            get_provider(top N) ─► reviews go to a separate checker
               ▼
          COMPARING ── model ranks the top 3, user picks one
               ▼
          HOLDING ──── hold_slot ─► quoted price ≠ search price? tell the user
               ▼
          AWAITING_APPROVAL ── code shows an approval card {action, provider, slot, price}
               │                fingerprint = hash(those fields); approval can be used once
               │   user confirms ─► code checks fingerprint == current hold and hold not expired
               ▼
          BOOKING ── save {idempotency_key, hold_id} to the DB first ─► book()
               ├─ success      ─► get_booking_status ─► CONFIRMED ✅
               ├─ slot_taken   ─► back to COMPARING (new approval needed)
               ├─ timeout      ─► get_booking_status(key): booked? confirmed : retry with SAME key (capped)
               └─ hold_expired ─► re-hold; slot or price changed? → AWAITING_APPROVAL again
               ▼
          DONE (+ update memory, close the trace)
```

The other flows reuse the same approval and booking machinery:
- **Reschedule** ("Move my AC servicing to Saturday"): `list_bookings` → find the right booking → approval → `reschedule(key)`. If it returns `slot_conflict`, offer other slots and get a new approval.
- **Same provider as before** ("same electrician as last time"): `list_bookings` → most recent electrician → that provider's slots, filtered to ≥10:00.
- **Cancel**: approval → `cancel(key)`. The first call returns a 503; the retry with the same key succeeds.
- **Proactive cancellation**: a simulated `provider_cancelled` event → background watcher → state `REPLACING` → search using stored preferences → notify the user with options → fresh approval → book.
- **Restart recovery**: on startup, look for any `BOOKING` records still marked in-progress, call `get_booking_status`, and settle each one before taking new messages.

**Notes on the Opus 5.5 API:**
- You can't force a specific tool call (`tool_choice: any/tool` returns an error). Use `auto` with `strict: true` tool schemas, or structured output for the step that extracts the user's details.
- Thinking can't be turned off. Set `effort` to `low` or `medium` so chat stays fast.
- For prompt caching, put the fixed parts first (tools, system prompt) and the changing parts after (memory, recent turns).
- Calculate cost from the token usage the API returns times a price table.
- Use the `count_tokens` API to calibrate token counts while online. Offline evals use a conservative local estimate with a safety margin.

**A second agent with a real job:** a separate review checker. It reads the raw provider reviews and can only return structured fields: a sentiment summary, flags, and `injection_suspected: bool`. The main agent never sees the raw review text. This is a well-known defence against prompt injection and gives a solid answer to "why more than one agent".

#### 4. Key mechanisms

- **Approval fingerprint**: a hash of `(action, provider_id, slot, quoted_price, booking_id)`. It's stored with `status=pending`, and the code marks it `consumed` in one atomic step. If the hold's price or slot changes, the fingerprint no longer matches and the approval is void.
- **Idempotency key**: derived from the approval ID and saved to the DB *before* `book` is called. The mock's `book` and `cancel` return the existing result when they see the same key again. That one rule covers repeated "yes", retries and restarts.
- **Memory record**: `{id, key, value, source: explicit|inferred, confirmed, status: active|superseded|forgotten, category, updated_at}`. A correction marks the old record `superseded` and adds a new one. Forgetting sets `status=forgotten` and the record is never retrieved again.
- **Context builder**: filters to active memories that are explicit or confirmed-inferred, ranks them by relevance to the current service, then adds a summary of older chat plus the last few turns, up to the budget. It writes a list of exactly which memory IDs and turns were sent into the trace, and the tests check that list.
- **Limits**: for example, 8 model turns, 15 tool calls and 60 seconds per user message. Each tool has a timeout and up to 2 retries with backoff. Hitting any limit gives a clear "here's where we are" message, never silence.

- **Confirm/yes** → the agent calls `book()`, and the provider uses the armed behaviour instead of a random one.
- After firing once, it's used up, and the next booking goes back to normal (random).

**Why it exists:** a real provider times out only by chance, so you can't show it reliably in a demo. Arm lets you trigger a specific failure on cue, so the audience sees how the agent handles it.

**What it isn't:** Arm doesn't touch the agent. The agent doesn't know anything is armed and handles the failure exactly as it would a real one. That's what makes the demo honest.

The dropdown options:

| Option | What the provider does on `book()` |
|---|---|
| success | Books it normally |
| timeout (actually booked) | Books it, but the reply "gets lost" |
| timeout (not booked) | Doesn't book, and the reply "gets lost" |
| slot taken | Refuses: someone else got that slot |
